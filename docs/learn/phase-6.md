# Фаза 6 — плагины и скрипты

Этот документ для тех, кто знает базовый Rust и прочитал `phase-0.md` … `phase-5.md`. Он
объясняет, как FormCraft расширяется снаружи: внешними скриптами (Python через control channel) и
плагинами-add-in'ами (WebAssembly-компоненты в песочнице), и почему сделано именно так. Заодно
разобрана математика эвольвентной шестерни из примера. Первоисточники: `PLAN.md` (п. 3А и
«Фаза 6»), `docs/adr/0003-plugin-api-v1.md` (включая раздел «Реализация»),
`docs/plugins/README.md`, крейты `crates/plugin-api` и `crates/plugin`.

## Что сделано

- Крейт `formcraft-plugin-api` (`crates/plugin-api`): WIT-описание API v1
  (`wit/formcraft.wit`, пакет `formcraft:plugin@1.0.0`) и манифест `plugin.toml` с проверкой
  (`Manifest::parse`, `valid_id`, совместимость по семверу).
- Крейт `formcraft-plugin` (`crates/plugin`): хост на `wasmtime` — загрузка, песочница, лимиты
  памяти и времени, регистрация команд и фич, выгрузка упавших плагинов, установка из `.zip`.
- Движок и перестроение: `FeatureKind::Custom` с «замороженным» телом, `Status::Warning`,
  трейт `CustomFeatures` (`crates/regen`), `Session::add_custom_feature`, `eval_params`,
  `set_custom_features` (`crates/engine`), base64 для замороженных тел (`crates/kernel/src/b64.rs`).
- Три примера в `examples/plugins/`: `gear` (шестерня, custom feature), `material` (команда
  `material.mass`), `spin` (намеренно «плохой», для тестов песочницы).
- Python-пакет `formcraft` (`python/formcraft/__init__.py`, только stdlib) и пример скрипта
  `examples/scripts/export_stl.py`.
- Диалог Scripts and Add-Ins (Shift+S, `crates/ui-egui/src/addins.rs`), автозагрузка плагинов
  при старте приложения (`app.rs`, `start_plugins`), логи плагинов.
- CLI: `formcraft-cli plugin install|list|new`, глобальные `--plugin <dir>` и `--no-plugins`;
  приложение тоже понимает `--plugin <dir>` и `--control PORT`.
- Документация для авторов `docs/plugins/README.md`.

Снимок: `docs/images/ui/9-addins-dark.png` — диалог Scripts and Add-Ins (вкладки ADD-INS и
SCRIPTS) в тёмной теме.

## Ключевые понятия

**Скрипт и плагин — две разные вещи.** Скрипт — отдельная программа (обычно Python), которая
подключается к уже запущенному FormCraft по TCP на `127.0.0.1` и шлёт команды. Плагин
(Add-In) — кусок кода, который загружается внутрь приложения и добавляет в него новые команды и
новые виды фич. Скрипту удобно «прогнать 50 экспортов», плагину — «добавить в программу фичу
Шестерня, которая перестраивается при смене параметра».

**WebAssembly (wasm).** Компактный бинарный формат команд для виртуальной машины. Код из wasm
не может сам обратиться к файлам, сети или памяти хоста: у него есть только своя линейная
память и те функции, которые хост явно дал. Поэтому «дырок» нет по умолчанию, а не «закрыты
отдельно».

**Core-модуль и компонент.** Обычный wasm-модуль (core module) понимает только числа: функции
принимают и возвращают `i32/i64/f32/f64`, а строки и структуры приходится вручную класть в
память и передавать указатель с длиной. Компонент (component model) — обёртка над модулями с
типизированным интерфейсом: строки, списки, записи, `result<T, E>`, ресурсы. Хост и гость
договариваются о типах, а склейку генерирует компилятор. Мы выбрали компоненты, чтобы не
писать ручную работу с памятью и получить типизированный ресурс `solid` для геометрии.

**WIT (WebAssembly Interface Types).** Язык описания интерфейса компонента. Файл
`crates/plugin-api/wit/formcraft.wit` — единый контракт: интерфейсы `types`, `geometry`, `host` и
мир (`world`) `plugin`, в котором перечислено, что плагин импортирует от хоста (`import host`,
`import geometry`) и что экспортирует (`init`, `run-command`, `regenerate`).

**Две стороны генерации биндингов.**

- *Гость* (плагин) использует `wit_bindgen::generate!` — макрос создаёт типы и трейт `Guest`,
  который плагин реализует (`impl Guest for Gear`), и `export!(Gear)`. См.
  `examples/plugins/gear/src/lib.rs`.
- *Хост* (наше приложение) использует `wasmtime::component::bindgen!` — макрос создаёт структуру
  `Plugin` с методами `call_init`, `call_run_command`, `call_regenerate` и трейты `Host`, которые
  хост реализует для функций, импортируемых плагином. См. `crates/plugin/src/host.rs`.

Оба макроса читают один и тот же `.wit`, поэтому рассогласовать типы нельзя.

**Ресурсы и хэндлы.** `solid` в WIT объявлен как `resource`. Геометрия (`Shape` из OCCT)
остаётся в памяти хоста, внутри `ResourceTable`; плагин получает только число-хэндл и вызывает
методы (`fuse`, `cut`, `transformed`…). Плагин не может ни подделать указатель на чужую память,
ни положить в хэндл что-то своё. Хост при этом валидирует каждый вызов: ошибка ядра — это
`Err(String)` для плагина, а не падение.

**WASI.** Стандартный набор системных вызовов для wasm (часы, случайные числа, файлы, стандартные
потоки…). Плагин собирается под таргет `wasm32-wasip2` и ожидает WASI preview 2. Хост добавляет его
в линкер (`wasmtime_wasi::p2::add_to_linker_sync`), но контекст создаётся пустым:
`WasiCtx::builder().build()` — без предоткрытых папок, без сети, без переменных окружения.

**Песочница и capabilities.** Плагин может только то, что ему явно выдали. Выдаётся три вещи:
вызовы `host.*` (команды, `inspect`, лог), геометрия `geometry.*` и файлы — только папки из
`[permissions] files` манифеста и только через `host.read-file` / `host.write-file`. Сеть в API v1
запрещена полностью (манифест с `network = true` отвергается).

**Лимит памяти.** `StoreLimits` с `memory_size(256 МиБ)`. Рост памяти выше лимита приводит к ошибке в
плагине, а не в хосте.

**Epoch interruption.** Механизм wasmtime для ограничения времени. Движок увеличивает счётчик
«эпохи» (`Engine::increment_epoch`); у `Store` задан дедлайн в тиках; при превышении код плагина
прерывается трапом `Trap::Interrupt`, даже если он крутится в бесконечном цикле. Это почти
бесплатно по сравнению с подсчётом инструкций. У нас отдельный поток `plugin-epoch` делает тик
каждые 10 мс.

**Почему не нативные DLL.** У Rust нестабильный ABI; DLL выполняется в нашем процессе с полными
правами и при падении убивает приложение; её нельзя ограничить по памяти и времени. Плагины на
wasm безопаснее, переносимы между ОС и могут быть написаны на любом языке с поддержкой
компонентов. Встроенный Python или Lua отвергнуты по тем же причинам (нет лимитов, тяжёлая
сборка). Подробности — в «Рассмотренных вариантах» ADR 0003.

**Детерминизм перестроения.** Каждое перестроение модели вызывает `regenerate` у каждой custom
feature. Если результат зависит от времени, случайных чисел или внешнего состояния, модель будет
«дрожать» между пересборками. Поэтому WASI дан без окружения, а контракт требует, чтобы
`regenerate` был детерминированной функцией параметров.

**Замороженное тело (frozen).** После первого успешного построения custom feature хранит в
документе сериализованное BREP-тело в base64 (`frozen`). Если плагина нет (не установлен,
выгружен, упал), фича строится из замороженного тела и получает статус `Status::Warning`
(«…; showing the last saved result») вместо ошибки. Файл можно открыть на машине без плагина, и
модель не развалится.

**Эвольвентная шестерня.** Подробно в разделе про `gear` ниже.

## Как это работает

### Манифест и API-версия

`crates/plugin-api/src/lib.rs`. Манифест `plugin.toml` читается в `Manifest::parse`:

```toml
id = "gear"
name = "Spur Gear"
version = "1.0.0"
api = "1.0"
wasm = "gear.wasm"

[permissions]
files = []
network = false
```

Проверки (`validate`): id — строчные ASCII-буквы, цифры, `_` и `-`, до 32 байт, начинается с
буквы (`valid_id`); `wasm` — просто имя `.wasm` файла рядом, без `..` и подпапок; `network = true`
отвергается; неизвестные ключи запрещены (`deny_unknown_fields`); размер манифеста не больше 64 КиБ.
Версия API сравнивается как семвер: мажор не совпал или минор новее хоста — `ManifestError::Incompatible`
с текстом «plugin `x` is built for API 2.0, this FormCraft supports API 1.x». Это правило из ADR:
несовместимый плагин не загружается, и причина понятна. Добавление нового экспорта в 1.x —
совместимое изменение, поэтому панели и события (`panel`, `on-event`) отложены до API 1.1.

### Загрузка: `Plugins::load`

`crates/plugin/src/lib.rs`.

1. `Plugins::new` создаёт `Engine` с `wasm_component_model(true)` и `epoch_interruption(true)`,
   линкер с WASI p2 и нашими `host`/`geometry`, и поток-тикер.
2. `load` читает `plugin.toml`, проверяет, что такой id ещё не загружен, и читает `.wasm`.
   `Component::new` отвергает мусор («not a valid component»).
3. Для плагина создаётся свой `Store<HostState>`: пустой WASI, `StoreLimits`
   (память 256 МиБ, не больше 4 экземпляров), список разрешённых папок, лог (последние 500 строк).
   Сразу ставится дедлайн `init` — 10 с.
4. `Bindings::instantiate` и вызов `init`: плагин возвращает списки команд (`command-spec`) и
   фич (`feature-spec`) вместе с JSON-схемами параметров.
5. `command_spec` проверяет, что id начинается с `<plugin>.` и схема — JSON-объект. Всё
   регистрируется в реестре сессии с источником `Source::Plugin(id)`. Регистрация «всё или
   ничего»: при ошибке на любой команде всё снимается обратно (`unregister_source`).
6. `s.set_custom_features(Some(plugins))` подключает хост как провайдера custom features.

Так как схемы лежат в реестре, команды плагина без единой правки кода появляются в окне S,
MCP `list_commands`, CLI и промпте ИИ (флаг `ai: true`). Тест `assistant_uses_the_gear_addin`
проверяет это на цепочке «промпт → план → фича».

### Лимиты: `Loaded::call`

Любой вход в плагин идёт через `Loaded::call(timeout, f)`: ставится дедлайн в тиках
(`ticks(timeout)`, по умолчанию 2 с на вызов, 10 с на `init`), под замком `Mutex<Store>`
выполняется `f`. Если `f` вернул ошибку, различаются два случая: `Trap::Interrupt` — «timed out
after N ms», иначе «crashed: …» (паника в плагине, переполнение памяти, неверный вызов). В обоих
случаях плагин помечается мёртвым (`kill`): `dead = true`, причина в `failure`, дальнейшие
вызовы сразу возвращают ошибку «was unloaded». Приложение продолжает работать.

Замок берётся через `try_lock`: плагин, который через `host.execute` запустил команду,
вызывающую его же, получил бы взаимную блокировку, поэтому вместо неё возвращается ошибка
«busy (re-entrant call)».

После падения `Plugins::reap(session)` снимает из реестра команды всех мёртвых плагинов и
возвращает пары (id, причина) для статуса и лога. А `unload` — то же по просьбе пользователя.

### Сессия «в долг» и `host.execute`

`run_command` в `lib.rs`: плагину нужно менять модель командами, но `Session` принадлежит
вызывающему и передан как `&mut`. Решение — `std::mem::take(s)`: сессия на время вызова
перекладывается в `HostState.session`, плагин вызывает `host.execute` / `host.inspect`, которые
берут её оттуда, а после вызова (в том числе после трапа) хост кладёт её назад. Никакого
`unsafe`. Вне вызова команды `host.execute` вернёт ошибку «the model is only available while a
plugin command runs». Все изменения проходят через тот же `Session::execute`, поэтому
undo работает как обычно, а параметры проверяются по схемам.

### Фичи плагина исполняет хост

Это важное отличие от черновика ADR. Для `feature-spec` хост регистрирует команду
`<plugin>.<kind>` (например, `gear.spur`), но её обработчик — не вызов плагина, а код хоста:
он разбирает «операцию с телом» (`body_op`: новое тело, объединить, вырезать, пересечь — как у
родных фич) и вызывает `Session::add_custom_feature`. Тот сам вызывает `regenerate` плагина один
раз, чтобы получить тело и заморозить его. Причина: к моменту перестроения плагин всегда «свободен»,
так что `regenerate` никогда не оказывается повторным входом в занятый экземпляр.

`Session::add_custom_feature` (`crates/engine/src/lib.rs`): вычисляет выражения в параметрах
(`eval_params` превращает строки-выражения вроде `"z"` в числа по таблице параметров),
вызывает `regenerate`, сериализует тело в BREP, кодирует в base64 (`kernel::b64::encode`) и
добавляет `FeatureKind::Custom { plugin, kind, params, op, frozen }` одним шагом undo. Параметры
в документе хранятся как введены пользователем (с выражениями), а плагин получает уже числа. Поэтому
`teeth = "z"` перестраивается при изменении `z`.

### Перестроение и запасной вариант

`crates/regen/src/lib.rs`, ветка `FeatureKind::Custom`: параметры вычисляются, у провайдера
`ctx.custom` (трейт `CustomFeatures::regenerate(plugin, kind, params) -> Result<Shape, String>`)
запрашивается тело. Если вышло — оно применяется как любая другая фича. Если нет, а `frozen`
есть — тело раскодируется (`b64::decode`) и десериализуется, а в статус попадает
`Warning("…; showing the last saved result")`. Если и замороженного тела нет — обычная ошибка.
Сам `Plugins` реализует `CustomFeatures`: находит плагин, вызывает `call_regenerate` с дедлайном и
забирает решение из таблицы ресурсов (`take_solid`).

### Хост: `host.rs`

Здесь `bindgen!` и реализации `Host` для `HostState`:

- `host.execute / inspect / log / read-file / write-file`. Лог режется (2000 символов на
  строку, 500 строк), файлы проверяются в `allowed`: нет `..`, путь внутри одной из разрешённых папок,
  размер не более 64 МиБ.
- `geometry.make-box / make-cylinder / extrude` и методы ресурса `solid`
  (`mass-props`, `transformed`, `fuse`, `cut`, `common`). Все входные числа проверяются
  на конечность (`v3`), полигон — на 3…100 000 точек. Всё идёт в `Kernel` (OCCT) с обычными проверками.

### Установка из zip: `install.rs`

`install::from_zip`: ищет `plugin.toml` в корне архива или в одной папке верхнего уровня,
разбирает манифест, распаковывает во временную папку `.<id>.installing`, проверяя каждый путь
(допускаются только обычные компоненты, без `..` и абсолютных путей), лимиты 1000 файлов и
256 МиБ, наличие файла `wasm` из манифеста; затем атомарно переименовывает в `<plugins>/<id>/`,
заменяя старую версию. Папка по умолчанию — `install::default_dir`: `FORMCRAFT_PLUGINS`, иначе
`%APPDATA%/FormCraft/plugins`, иначе `$XDG_CONFIG_HOME/formcraft/plugins` или `~/.config/formcraft/plugins`.

### Приложение и CLI

- Старт приложения: `FormCraftApp::start_plugins` (`crates/ui-egui/src/app.rs`) создаёт
  `Plugins`, загружает `--plugin <dir>` и установленные плагины (`load_all`), ошибки пишет в статус.
- Диалог Scripts and Add-Ins (`crates/ui-egui/src/addins.rs`, Shift+S): вкладка ADD-INS —
  список плагинов с состоянием, командами и логом, установка из `.zip`, перезагрузка, выгрузка,
  «открыть папку»; вкладка SCRIPTS — Python-файлы, запуск против этого же приложения: оно само
  поднимает control channel на свободном порту и передаёт его скрипту в `FORMCRAFT_PORT`
  (`start_script`).
- CLI (`apps/formcraft-cli/src/main.rs`): `plugin install <zip>` (проверяет загрузку и печатает
  список команд), `plugin list`, `plugin new <имя> [--lang rust|python-script]` (шаблоны в
  `templates.rs`: `Cargo.toml`, `plugin.toml`, `src/lib.rs` с командой `<id>.hello` и фичей
  `<id>.block`, копия `wit/formcraft.wit`). Глобальные флаги: `--plugin <dir>` (можно несколько) и
  `--no-plugins`.

### Скрипты: Python-клиент

Протокол control channel (строка JSON `{id, method, params}` → `{id, result|error}`) появился в
Фазе 4 для MCP Remote и теперь это публичный API скриптов, менять его можно только совместимо.
`python/formcraft/__init__.py` — тонкая обёртка на `socket` без зависимостей:
`formcraft.connect(port)` (порт из `FORMCRAFT_PORT`, иначе 7878) возвращает `Client` с методами
`execute(command, **params)`, `commands()`, `inspect()`, `bodies()`, `parameter()`, `new/open/save`,
`export(path, bodies=…)`, `render(path, view=…)` и контекстным менеджером. Ошибки приложения
превращаются в `FormCraftError`. Пример `examples/scripts/export_stl.py` экспортирует каждое
видимое тело в свой STL.

Python в приложение не встроен: скрипт — отдельный процесс с обычными правами ОС, а изоляция
нужна именно плагинам, которые живут внутри процесса.

## Пример `gear`: эвольвентная шестерня

`examples/plugins/gear/src/lib.rs`. Плагин объявляет одну фичу `spur` (параметры: `teeth` — число
зубьев z, `module` — модуль m, `thickness`, `bore`, `pressure_angle`, `center`) и в
`regenerate` строит контур зубчатого колеса, выдавливает его на `thickness` вдоль оси Z через
`geometry.extrude` и при необходимости делает отверстие (контур-«дырка», обходится по часовой).

Терминология и формулы (см. функцию `outline`):

- **Модуль m** — мера размера зуба: диаметр делительной окружности равен `m·z`.
- **Делительная окружность** `r = m·z / 2`. Здесь толщина зуба равна ширине впадины.
- **Основная окружность** `rb = r·cos(α)`, где α — угол зацепления (по умолчанию 20°). Эвольвента
  «разматывается» с неё, как нить с катушки.
- **Окружность вершин (addendum)** `ra = r + m` — внешний край зуба.
- **Окружность впадин (dedendum)** `rf = r − 1.25·m` — дно впадины. Для совсем маленьких колёс
  значение подрезается снизу, чтобы радиус оставался положительным.
- **Эвольвентная функция** `inv(a) = tan(a) − a`. Нужна, чтобы получить полярный угол точки
  профиля на радиусе ρ: половина угла зуба на радиусе ρ равна
  `π/(2z) + inv(α) − inv(acos(rb/ρ))` (функция `half`). Левая и правая стороны зуба — зеркальные
  кривые `c ± half(ρ)` вокруг оси зуба `c = 2πk/z`.

Алгоритм контура: для каждого зуба `k` идём по левой стороне вверх от `max(rb, rf)` до `ra`
(8 шагов), по дуге вершины (4 отрезка), по правой стороне вниз и по дуге впадины к следующему
зубу. Если дно ниже основной окружности (`rf < rb`), добавляются радиальные участки от `rf` до
`rb`. Результат — один многоугольник против часовой стрелки.

Параметры проверяются: `teeth` целое 6…200, `module` 0.1…50, `pressure_angle` 10…35°, `bore`
меньше 90% диаметра впадин. Некорректные значения возвращают `Err`, а не падают (в тесте:
`teeth = 3` и `module = "nope"` дают ошибку). Функция детерминирована, зависит только от параметров.

## Как проверить

Тесты (wasm-файлы примеров лежат в репозитории рядом с манифестами, пересборка не требуется):

```
cargo test -p formcraft-plugin
cargo test -p formcraft-plugin-api
cargo test -p formcraft-ui-egui gear_addin
cargo xtask ci
```

Что проверяет `crates/plugin/src/tests.rs`:

- `gear_plugin_adds_a_parametric_feature` — загрузка, команда `gear.spur` в реестре с флагом `ai`,
  объём между кругами впадин и вершин, перестроение при смене параметра `z`, правка через
  `feature.edit`, враждебные параметры дают ошибку, после `unload` остаётся замороженное тело
  и `Status::Warning`.
- `bad_plugins_are_refused_cleanly` — нет манифеста, API 2.0, мусор вместо компонента; реестр
  остаётся нетронутым.
- `install_from_zip_checks_paths` — установка из zip и отказ на `../evil.wasm` и на архиве без
  `.wasm`.
- `misbehaving_plugins_are_unloaded_not_fatal` — приёмка Фазы 6: бесконечный цикл (`spin.forever`)
  прерывается по таймауту, сессия цела, `reap` снимает команды; `spin.hog` и `spin.panic` тоже
  только выгружают плагин.
- `assistant_uses_the_gear_addin` — промпт ИИ содержит `gear.spur`, план на Mock-бэкенде
  применяется, фича попадает в группу.
- `material_addin_computes_mass` — `material.mass` через `host.inspect`: 100 см³ алюминия — 270 г.

Тест интерфейса: `gear_addin_button_dialog_and_timeline` (`crates/ui-egui/src/app_tests.rs`) —
кнопка в группе Create, диалог из схемы, фича на таймлайне.

Сборка плагина-шестерни (нужен `rustup target add wasm32-wasip2`):

```
cd examples/plugins/gear
cargo build --release --target wasm32-wasip2
```

Итоговый файл — в `target/wasm32-wasip2/release/`; его нужно скопировать рядом с `plugin.toml` под
именем из поля `wasm` (`gear.wasm`), см. `docs/plugins/README.md`. Запуск приложения с плагином:

```
formcraft --plugin examples/plugins/gear
```

После этого в группе Create появится кнопка «Spur Gear», а в окне S — `gear.spur`; Shift+S открывает
Scripts and Add-Ins. Новый плагин-заготовка и установка:

```
formcraft-cli plugin new my_addin
formcraft-cli plugin install my_addin.zip
formcraft-cli plugin list
```

Скрипт против запущенного приложения:

```
formcraft --control 7878
python examples/scripts/export_stl.py C:/out
```

(порт 7878 — значение `FORMCRAFT_PORT` по умолчанию; другой порт задайте переменной окружения
`FORMCRAFT_PORT`). Скрипт выведет имя, объём и путь каждого экспортированного STL.

## Проверь себя

1. Чем скрипт принципиально отличается от плагина и когда выбирать какой?
2. Чем компонент отличается от core-модуля wasm и зачем нужен WIT?
3. Кто использует `wit_bindgen`, а кто `wasmtime::component::bindgen!`?
4. Что такое ресурс `solid` и почему плагин не может испортить геометрию хоста?
5. Что плагин может делать «из коробки», а что — только по манифесту?
6. Как обрывается бесконечный цикл в плагине и что происходит дальше?
7. Зачем сессия «одалживается» плагину через `std::mem::take`?
8. Почему фичи плагина исполняет хост, а не `run-command` плагина?
9. Что такое замороженное тело и когда пользователь видит предупреждение?
10. Что такое делительная и основная окружности и зачем в шестерне функция `inv`?

<details>
<summary>Ответы</summary>

1. Скрипт — отдельный процесс, управляет приложением через control channel; плагин загружается
   внутрь, живёт в песочнице и добавляет команды и фичи. Скрипт — для разовой автоматизации,
   плагин — для повторно используемых возможностей в интерфейсе.
2. Core-модуль знает только числа и память; компонент добавляет типы (строки, записи, `result`,
   ресурсы). WIT описывает эти типы и функции единым контрактом `formcraft.wit`, из него
   генерируются биндинги для гостя и хоста.
3. Плагин (гость) использует `wit_bindgen::generate!` и реализует `Guest`; хост использует
   `wasmtime::component::bindgen!` и реализует трейты `Host` для импортируемых функций.
4. Это ресурс-хэндл: тело `Shape` лежит в `ResourceTable` хоста, плагин видит только число и
   вызывает проверяемые методы. Ошибки ядра возвращаются как `Err`.
5. По умолчанию — команды хоста, `inspect`, лог, геометрия. Папки для чтения и записи — только
   те, что перечислены в `[permissions] files`; сети нет вообще.
6. Тикер раз в 10 мс увеличивает эпоху; дедлайн (2 с на вызов) истекает, wasmtime прерывает
   выполнение трапом `Interrupt`. Плагин помечается мёртвым, `reap` снимает его команды, приложение
   продолжает работать.
7. `host.execute` должен менять сессию вызывающей стороны без `unsafe` и без двойного заимствования.
   Сессия перекладывается в состояние плагина на время вызова и возвращается после него, в том числе
   после трапа.
8. Чтобы при перестроении `regenerate` не вызывался, пока плагин занят: тогда повторного входа
   в один экземпляр не бывает.
9. Это сохранённое в документе BREP-тело (base64), последний успешный результат. Если плагина нет
   или он упал, фича строится из него, а на таймлайне показывается `Status::Warning`.
10. Делительная окружность `r = m·z/2` — по ней измеряется модуль; основная `rb = r·cos α` — с неё
    «разматывается» эвольвента. Функция `inv(a) = tan a − a` даёт полярный угол точки эвольвенты,
    чтобы построить симметричные стороны зуба.

</details>
