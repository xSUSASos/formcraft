# Фаза 1 — каркас и оболочка интерфейса в стиле Fusion

Этот документ для тех, кто знает базовый Rust, но не писал GUI на egui и не работал с 3D-камерами.
Он объясняет, как устроен workspace, как проверяются слои, зачем нужен реестр команд и как работает
оболочка окна: панели, камера, ViewCube, темы и тесты на симулированной мыши.
Первоисточники: `PLAN.md` (§2 и §4), `docs/architecture.md`, `docs/adr/0002-dependency-licenses.md`.

## Что сделано

- Собрали workspace с крейтами по слоям L0–L8 (`docs/architecture.md`) и инструмент `cargo xtask`
  с командами `ci`, `layers`, `deny`.
- Настроили GitHub Actions (`.github/workflows/ci.yml`): `cargo xtask ci` на `windows-latest` и
  `ubuntu-latest`.
- Записали политику лицензий в `deny.toml` (только permissive-лицензии, два исключения).
- Написали реестр команд в `crates/engine/src/registry.rs`: каждое действие — команда с JSON-схемой.
- Нарисовали раскладку из `PLAN.md` §2: application bar, toolbar с вкладками, browser,
  canvas с сеткой, ViewCube, navigation bar, timeline, сворачиваемая панель text commands.
- Написали орбитальную камеру (`crates/render/src/camera.rs`) и адаптивную сетку (`grid.rs`).
- Сделали две темы на цветовых токенах (`theme.rs`) и сохранение раскладки (`layout.rs`).
- Покрыли оболочку интерфейсными тестами на `egui_kittest` (`app_tests.rs`) и добавили флаг
  `--screenshot` для снимков окна.

Снимки результата: `docs/images/phase1-dark.png` (тёмная тема, раскладка по умолчанию) и
`docs/images/phase1-light-floating-top.png` (светлая тема, браузер вынесен в плавающее окно,
вид сверху).

## Ключевые понятия

**Immediate-mode UI** — стиль интерфейса, где нет дерева виджетов, живущего между кадрами. Каждый
кадр код заново «рисует» интерфейс вызовами вроде `ui.button("OK")`, а результат (нажата ли кнопка)
возвращается сразу. Состояние (открыта ли панель, какой режим) хранит ваша структура, а не виджеты.
egui устроен именно так; `FormCraftApp::draw` вызывается на каждом кадре.

**Реестр команд** — таблица «id команды → описание + обработчик». Описание (`CommandSpec`) содержит
id вроде `solid.extrude`, подпись, подсказку, JSON-схему параметров, место на toolbar, горячую
клавишу и флаги `ai` и `undoable`. Обработчик — `Fn(&mut Session, &Value) -> Result<Value>`:
JSON на входе, JSON на выходе.

**Орбитальная камера** — камера, которая смотрит на точку-цель (`target`) с расстояния `distance`
и вращается вокруг неё по двум углам: `yaw` и `pitch`. В CAD ось Z направлена вверх.

**ViewCube** — маленький куб в углу холста, повторяющий ориентацию камеры; клик по его грани,
ребру или углу ставит камеру в стандартный вид.

**Токены темы** — именованные цвета (`canvas_top`, `accent`, `error`, …). Код интерфейса берёт
цвета только оттуда, поэтому смена темы — это подмена одной таблицы.

## Слои и проверка `cargo xtask layers`

Слои из `docs/architecture.md` и `xtask/src/layers.rs` (таблица `LAYERS`):

| Слой | Крейты |
|---|---|
| L0 | `kernel`, `plugin-api` |
| L1 | `occt`, `sketch` |
| L2 | `doc` |
| L3 | `regen`, `tess` |
| L4 | `io` |
| L5 | `engine` |
| L6 | `ai`, `plugin`, `render` |
| L7 | `ui-egui`, `mcp` |
| L8 | приложения `formcraft`, `formcraft-cli` |

Как работает проверка (`layers::check`):

1. `cargo xtask layers` запускает `cargo metadata --no-deps` и получает JSON со всеми крейтами
   workspace и их зависимостями.
2. Для каждого крейта ищется его слой по имени (префикс `formcraft-` отбрасывается). Крейт без
   слоя — уже нарушение: «not assigned to a layer».
3. Для каждой обычной зависимости (dev-зависимости пропускаются) проверяется, что слой зависимости
   строго меньше слоя крейта. Иначе сообщение вида `X (L5) depends on Y (L5)`.
4. Крейтам ниже L7 запрещены `egui`, `eframe`, `egui-wgpu`, `egui-winit`, `winit`, `rfd` и
   `egui_kittest` (список `UI_ONLY`).

Зачем так жёстко: движок и документ должны работать без окна — из CLI, из MCP-сервера, из плагинов.
Если бы `engine` зависел от egui, консольная программа тянула бы весь GUI-стек.

## Что делает `cargo xtask ci`

Шаги идут по порядку и останавливаются на первой ошибке (`xtask/src/main.rs`, функция `ci`):

1. `fmt` — `cargo fmt --all -- --check`;
2. `clippy` — `cargo clippy --workspace --all-targets -- -D warnings` (предупреждения = ошибки);
3. `test` — `cargo test --workspace`;
4. `layers` — проверка выше;
5. `deny` — `cargo deny check licenses bans sources`.

В конце печатается сводка «CI summary». Тот же `cargo xtask ci` запускает GitHub Actions
(Windows и Linux), поэтому локальная и серверная проверка не расходятся.

## Реестр команд: почему он наполняется в рантайме

Можно было бы написать `enum Command { Extrude, Fillet, ... }` и `match` в UI. Мы не делаем так
(правило в `CLAUDE.md`: никаких жёстко прописанных списков команд). Причины:

- Плагины (Фаза 6) добавляют команды после старта. Статический `enum` об этом не знает, а
  `Registry::register` можно вызвать в любой момент, и `unregister_source` убирает все команды плагина.
- ИИ (Фаза 5) получает список команд и их JSON-схемы прямо из реестра. Новая команда
  автоматически становится ему доступна.
- Один и тот же набор видят UI, окно поиска по S, MCP, CLI и скрипты. Нельзя забыть добавить
  команду «ещё и в меню».

Что проверяет `register`: id состоит из строчных ASCII-букв, цифр, `_`, `-`, разделённых точками
(`valid_id`, до 64 байт); схема параметров — JSON-объект; дубликат id — ошибка, то есть плагин не
может подменить встроенную команду. Реестр хранится в `BTreeMap`, поэтому порядок списка стабилен.

Toolbar (`toolbar.rs`) показывает встроенные команды в порядке Fusion; если команда ещё не
зарегистрирована, её кнопка отображается выключенной. Команды из плагинов с подходящим
`Placement { tab, group, pinned }` дописываются в свою группу.

## Интерфейс на egui: порядок панелей

В egui панели занимают место в порядке вызова: **сначала внешние, потом внутренние**, а
`CentralPanel` получает то, что осталось, и вызывается последним. Метод `FormCraftApp::draw`:

1. `app_bar` — `Panel::top`, самая верхняя полоса;
2. `toolbar` — `Panel::top` под ней;
3. `timeline` — `Panel::bottom`, **самая нижняя**, потому что объявлена раньше остальных нижних;
4. `text_commands` — `Panel::bottom` над timeline (у неё есть ещё узкая полоска-заголовок);
5. `browser` — `Panel::left`; в режиме Floating рисуется как окно;
6. `CentralPanel` с прозрачной заливкой — холст (`canvas`).

Если поменять местами пункты 3 и 4, timeline окажется над консолью, а не под ней. Холст прозрачен,
чтобы был виден градиент фона (`canvas_top` → `canvas_bottom`), который рисует интерфейс, а не
3D-рендерер. Поверх холста рисуются ViewCube (`viewcube.rs`) и navigation bar (`nav_bar`).

Состояние между кадрами живёт в `FormCraftApp`: активная вкладка, режим навигации
(`NavMode::Select/Orbit/Pan/Zoom`), `Layout`, `Camera`, `Session` движка. UI тонкий: действия идут
через `self.run(id, params)`, то есть через реестр команд.

## Орбитальная камера

Код: `crates/render/src/camera.rs`. Ось Z вверх. Поля: `target`, `distance`, `yaw`, `pitch`,
`fov_y`, `projection` (перспектива или ортография).

- **Углы.** `yaw` вращает вокруг +Z (0 — взгляд вдоль +Y), `pitch` — возвышение (плюс — смотрим
  сверху). Вектор от цели к глазу — `back()`, глаз — `eye() = target + back() * distance`.
- **`pitch` ограничен** значением чуть меньше 90° (`FRAC_PI_2 - 1e-4`), чтобы не попасть в
  вырожденный случай «взгляд строго вдоль Z», где «вправо» не определено. На такой случай
  `right()` возвращает ось X.
- **`look_from(dir)`** ставит камеру так, чтобы глаз лежал в направлении `dir` от цели: из
  направления взгляда считаются `pitch = asin(-f.z)` и `yaw = atan2(f.x, f.y)`. Нулевой или
  нечисловой вектор игнорируется. Home-вид — `look_from((1, -1, 1))` при расстоянии 300.
- **Орбита:** сдвиг мыши в пикселях умножается на 0.008 рад/пиксель; `pitch` зажимается в допустимые
  пределы.
- **Пан в плоскости экрана:** сколько мировых единиц в пикселе, зависит от `distance`:
  `world_per_px = 2 * half_height / height_px`. Цель сдвигается по векторам `right()` и `up()`
  камеры, а не по осям мира.
- **Зум к курсору:** шаг колеса даёт множитель `0.85^steps`. Чтобы точка под курсором («якорь»)
  осталась на месте, цель подтягивается к ней на долю `k = 1 - new_distance / distance`. В
  интерфейсе якорь — пересечение луча из курсора с плоскостью `z = 0`, а если оно далеко или за
  спиной — точка на глубине цели (`cursor_anchor`).

Управление как во Fusion: Shift + средняя кнопка — орбита, средняя кнопка — пан, колесо — зум
к курсору, двойной клик средней кнопкой — Fit.

## ViewCube: 3×3 клетки и 26 видов

Каждая видимая грань куба делится на сетку 3×3 (`INNER = 0.6` — доля полуразмера для средней
клетки). Клетка `(i, j)` с `i, j ∈ {-1, 0, 1}` задаёт направление «от модели к глазу»:
`d = n + a*i + b*j`, где `n` — нормаль грани, `a`, `b` — оси грани. Число ненулевых компонент `d`
равно 1, 2 или 3:

- центр грани → вид на грань (6 штук: TOP, FRONT, …);
- боковая клетка → вид на ребро (12);
- угловая клетка → вид на угол (8).

6 + 12 + 8 = 26 — это все ненулевые векторы с компонентами из {-1, 0, 1}; `CubeView::all()`
перебирает их циклом. Тест `every_cell_maps_to_one_of_26_views` проверяет, что клетки достигают
всех 26. Клик вызывает `camera.look_from(view.dir())`; кнопка Home возвращает вид `Camera::home()`.
Куб рисуется своей проекцией по `cam.right()` и `cam.up()`, грани сортируются от дальних к ближним.

## Темы, раскладка и «враждебные» значения

**Темы.** `Tokens::get(ThemeKind)` возвращает структуру цветов для Dark или Light, а
`Tokens::visuals()` превращает её в `egui::Visuals`. `draw` выставляет их каждый кадр. Рендерер
получает цвета сетки и осей из тех же токенов.

**Раскладка.** `Layout` (`layout.rs`) хранит тему, состояние панелей (`open`, `Docked/Floating`,
размер), флаги nav bar, ViewCube, сетки и визуальный стиль (Shaded, Shaded with Edges, Wireframe).
Сохраняется через `eframe::set_value` в `save`, читается в `FormCraftApp::new`. `#[serde(default)]`
значит, что поля, которых нет в файле, берут значения по умолчанию. «Reset layout» (`reset()`)
возвращает умолчания, но оставляет тему.

**`sanitize()`.** Сохранённый файл могут отредактировать или повредить, поэтому размеры панелей
зажимаются: браузер 150–700, timeline 36–120, text commands 80–600, ассистент 200–700; не-число
заменяется значением по умолчанию. Тест `stored_layout_is_sanitised` подаёт `size: 1e30` и `-5` и
проверяет границы 700 и 36. Камера из хранилища принимается, только если `distance` конечно.

## Интерфейсные тесты на egui_kittest

`crates/ui-egui/src/app_tests.rs` создаёт `Harness` с размером 1440×900 и шлёт в него события
`egui::Event`: `PointerMoved`, `PointerButton`, `MouseWheel`, `ModifiersChanged`. Окно и GPU
не нужны. Вспомогательные функции `drag` и `click` разбивают жест на шаги (нажатие, пять
перемещений, отпускание), потому что egui распознаёт drag по нескольким кадрам. Проверки идут по
состоянию `h.state()`:

- `shift_middle_drag_orbits`: `yaw` изменился, `target` тот же;
- `middle_drag_pans`: `target` сместился, `yaw` тот же;
- `wheel_zooms_in_and_out`: колесо вверх уменьшает `distance`, вниз увеличивает;
- `view_cube_top_face_sets_top_view`, `browser_float_close_and_reset`,
  `text_command_line_runs_commands`, `both_themes_render`.

## Скриншоты через `--screenshot`

`formcraft --screenshot out.png` включает свежую раскладку (`fresh_layout`), на пятом кадре
посылает `ViewportCommand::Screenshot`, сохраняет полученное изображение как PNG и закрывает
окно. Остальные флаги из `apps/formcraft/src/main.rs`: `--theme dark|light`, `--float-browser`,
`--text-commands`, `--view top|front|right|home`, `--script файл`. Так сделаны снимки в `docs/images/`.

## Проверь себя

1. Почему `engine` не может зависеть от `eframe`, и какой шаг CI это поймает?
2. Где в `draw` вызывается `timeline` и почему именно там?
3. Что произойдёт, если в файле раскладки записано `"size": 1e30` для браузера?
4. Сколько видов у ViewCube и из каких групп они складываются?
5. Зачем при зуме к курсору сдвигается цель камеры?

<summary>Ответы</summary>

1. `engine` — слой L5, а `eframe` разрешён только слоям L7 и выше (`UI_ONLY`). Ловит шаг
   `layers` в `cargo xtask ci`; он же сообщит о зависимости от крейта того же или верхнего слоя.
2. Сразу после `toolbar`, до `text_commands`, `browser` и `CentralPanel`. Нижние панели
   занимают место в порядке вызова, поэтому первая объявленная оказывается самой нижней.
3. `sanitize()` зажмёт размер до максимума 700 (см. тест `stored_layout_is_sanitised`).
4. 26: 6 граней, 12 рёбер и 8 углов — ненулевые векторы с компонентами из {-1, 0, 1}.
5. Чтобы мировая точка под курсором осталась на том же месте экрана; иначе картинка «уплывала»
   бы к центру при каждом шаге колеса.
