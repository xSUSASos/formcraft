# Фаза 5 — встроенный ИИ

Этот документ для тех, кто знает базовый Rust и прочитал `phase-0.md` … `phase-4.md`. Он
объясняет, как в FormCraft устроен локальный ИИ-помощник: как запрос на человеческом языке
превращается в группу фич на таймлайне, почему это безопасно и как измеряется качество. Заодно
описано выравнивание интерфейса по `UI_SPEC.md`, сделанное в тот же период. Первоисточники:
`PLAN.md` (п. 3 и «Фаза 5»), `UI_SPEC.md` §5.12, `PROGRESS.md`, `docs/adr/0004-ui-spec.md`,
крейт `crates/ai`, `crates/ui-egui/src/assistant.rs`.

## Что сделано

- Крейт `formcraft-ai` (`crates/ai`): бэкенды LLM (Ollama, OpenAI-совместимый сервер, Mock),
  собственный минимальный HTTP-клиент, промпт и схема ответа из реестра команд, формат плана,
  конвейер «сгенерировать → проверить → исправить», логи, команды `ai.generate`, `ai.explain`,
  `ai.status`.
- Движок: `Session::fork` и `Session::transaction` (один шаг undo, группа фич), `Document::groups`.
- 28 few-shot примеров (`crates/ai/fewshot/*.json`), встроенных в бинарник при сборке.
- Панель Assistant (`crates/ui-egui/src/assistant.rs`) по `UI_SPEC.md` §5.12, фоновая генерация,
  превью цветом `ai`, кнопки Принять / Отклонить. Точки входа: строка ИИ в окне S, кнопка
  Generate на тулбаре, пункт «Edit with AI…» в marking menu, значок ✦ в app bar, «Explain» в
  контекстном меню фичи на таймлайне.
- CLI: `formcraft-cli ai "<запрос>"` и `formcraft-cli ai-bench`; `cargo xtask ai-bench`.
- Бенчмарк `ai-bench`: 50 случаев с эталонными планами (`crates/ai/bench/cases.json`).
- UI-выравнивание по `UI_SPEC.md` (ADR 0004): токены в `theme.rs`, светлая тема, шрифт Inter,
  иконки, рисуемые в коде, плавающие карточки, группа-папка ✦ на таймлайне, тосты ошибок,
  снимки сцен §8.

Снимки: `docs/images/ui/7-ai-group-light.png` — ИИ-группа на таймлайне и панель Assistant;
`docs/images/ui/6-shortcut-box-light.png` — окно S с фиолетовой строкой «Сделать с ИИ».

## Ключевые понятия

**LLM (большая языковая модель)** — программа, которая по тексту продолжает текст. Работает
локально: Ollama или llama.cpp загружают веса модели (у нас по умолчанию `qwen2.5-coder:7b`) и
отвечают по HTTP на `127.0.0.1`. Никакие данные не уходят в сеть.

**Почему модель выдаёт план из команд, а не код.** Код (Python, Rust) может сделать что угодно:
удалить файл, зависнуть, обратиться к сети. План — это JSON из имён команд и параметров, который
проверяется по тем же схемам, что и ручной ввод. Всё, что не из реестра, отклоняется до запуска.
К тому же команды уже умеют undo, перестроение и параметры, а ошибки возвращаются обычным
`Err`, а не падением. Это следствие правила «всё есть команда».

**Структурный вывод (structured output).** Мы отправляем серверу JSON-схему ответа (Ollama —
поле `format`, OpenAI-совместимый сервер — `response_format`). Сервер ограничивает генерацию
грамматикой: на каждом шаге модель может выбрать только токены, которые не нарушают схему.
Поэтому ответ всегда разбирается как JSON нужной формы, а поле `command` может содержать лишь id
из перечисления (`enum`) команд. Схема гарантирует форму, но не смысл: радиус скругления может
оказаться слишком большим. Для смысла нужен цикл исправления.

**Few-shot prompting.** Перед настоящим запросом модели показывают пары «запрос → правильный
план» как прошлые реплики диалога. Модель подражает формату и стилю. Выбирается не всё
подряд, а k=3 примеров, ближайших к запросу по совпадению слов (`fewshot::pick`).

**Цикл исправления (repair loop).** Если план не разобрался, не прошёл проверку или шаг упал при
применении, текст ошибки добавляется в диалог («That plan failed: … Fix the problem…»), и модель
пробует снова, максимум 3 попытки. Пользователь видит «Repairing (2/3)…».

**Температура.** Параметр случайности выбора токена. 0 — всегда самый вероятный токен, выше —
разнообразнее и ошибочнее. Для CAD нужна точность, поэтому по умолчанию 0.1.

**Контекстное окно (`num_ctx`).** Сколько токенов модель видит одновременно: системный промпт,
каталог команд, примеры, ваш запрос и ответ. Не влезло — начало обрезается. Мы просим у Ollama
8192. Растёт окно — растёт расход памяти и время.

**CPU и GPU.** Генерация токенов упирается в пропускную способность памяти. На видеокарте 7B-модель
отвечает за секунды, на процессоре — в разы медленнее. На dev-машине Ollama 0.40.4 не находит
RTX 4050 (`initial_count=0`), поэтому инференс идёт на CPU: короткий ответ ~14 с, полный прогон
фланца с тремя попытками — 4 мин 10 с (см. `PROGRESS.md`, «Требует человека»). Цель приёмки
«меньше 60 с» рассчитана на GPU с 12 ГБ VRAM.

**Fork сессии.** `Session::fork` (`crates/engine/src/lib.rs`) делает копию сессии: тот же
документ, реестр и ядро, но без истории undo. Весь генератор работает с копией; пользовательский
документ не меняется, пока он не нажмёт «Принять».

## Как это работает

### Конвейер

`crates/ai/src/pipeline.rs`, `Generator::generate`:

1. Собирается диалог (`messages`): системный промпт, 3 few-shot пары, затем контекст текущей
   модели и запрос. Контекст (`context`) — параметры со значениями, список фич, тела с bbox и
   объёмом, а при «Edit with AI…» ещё выбор: грань или ребро описаны центром, нормалью и готовым
   селектором `{"near": [x, y, z]}`.
2. `backend.chat` отправляет диалог со схемой плана и `temperature`, `max_tokens`.
3. `plan::parse` достаёт JSON из ответа, прощая блоки `<think>`, огораживание ```json и текст
   вокруг; голый массив принимается как список шагов.
4. `plan::validate` (до запуска): известные команды, только с флагом `ai`, `params` — объект,
   разумные размеры (до 60 шагов и 50 параметров), корректные имена параметров.
5. `plan::apply` на `base.fork()`: параметры → `doc.parameter`, шаги → `Session::execute`. Если
   после этого какая-то новая фича перестроилась с ошибкой, это тоже отказ.
6. Успех — `Proposal` (план, сессия-превью, список добавленных фич, попытки). Неудача — ошибка
   уходит в диалог, следующая попытка. После трёх — `AiError::Failed`.
7. Между шагами проверяется флаг отмены (`AtomicBool`) — кнопка «Стоп».

`Progress` (`Generating`, `Repairing`) передаётся в UI через колбэк; из него получается статус
«Генерация…» / «Repairing (2/3)…».

### Промпт из реестра

`crates/ai/src/prompt.rs`. Промпт не пишется руками: `catalog` обходит реестр и берёт только
команды с `ai`, `render_props` выводит параметры компактно, по строке на свойство
(`- diameter: number|expr (required) — …`). Малые модели читают это лучше сырой JSON-схемы, а
текста втрое меньше. `selectors_help` перечисляет имена граней и рёбер и объясняет `{"near":…}`.
`output_schema` строит схему ответа с `enum` из id команд. Команда плагина с `ai` попадёт в
промпт сама, без правок кода.

### План

`crates/ai/src/plan.rs`:

```json
{"summary": "Flange D100, 4 x D9",
 "parameters": [{"name": "flange_d", "expression": 100}],
 "steps": [{"command": "solid.cylinder", "params": {"diameter": "flange_d", "height": 10}}]}
```

Размеры вынесены в именованные параметры, шаги ссылаются на них выражениями — результат
параметрический: поменяли `flange_d`, и всё перестроилось.

### Одна транзакция, один undo, группа

`plan::apply` вызывает `Session::transaction(label, Some(group), …)`. При любой ошибке всё
откатывается; при успехе добавленные фичи получают общую группу с названием из `summary`
(`Document::groups`). На таймлайне это папка со значком ✦, раскрывающаяся скобкой; одно
`Ctrl+Z` убирает всю генерацию.

### Бэкенды и HTTP

`crates/ai/src/backend.rs`: трейт `LlmBackend` (`chat`, `status`, `kind`, `model`).

- `Ollama`: `POST /api/chat`, схема в `format`, `options` (`temperature`, `num_predict`,
  `num_ctx`), `stream: false`. `status` читает `/api/tags` и `/api/ps` (модель загружена, VRAM).
- `OpenAi`: `POST /v1/chat/completions`, схема в `response_format`. Подходит для
  `llama-server` и LM Studio.
- `Mock`: заготовленные ответы или функция от запроса, записывает запросы. Нужен тестам и CI.

Настройки (`AiConfig::from_env`): `FORMCRAFT_AI_BACKEND` (`ollama` | `openai`),
`FORMCRAFT_AI_URL`, `FORMCRAFT_AI_MODEL`, `FORMCRAFT_AI_TIMEOUT` (секунды).

`crates/ai/src/http.rs` — собственный минимальный HTTP/1.1-клиент (~140 строк). Зависимость
вроде `reqwest` тянет TLS и async-рантайм, а нам нужно одно: отправить JSON на локальный порт.
Клиент понимает `Content-Length`, `Transfer-Encoding: chunked` и чтение до закрытия соединения;
размер ответа ограничен 64 МБ, число строк заголовка — 200; принимается только `http://`
(облачные адреса вне MVP). Ошибка HTTP-статуса превращается в текст с сообщением сервера.

### Few-shot во время сборки

`crates/ai/build.rs` собирает список `fewshot/*.json` в `OUT_DIR/fewshot_files.rs`, файлы
встраиваются в бинарник через `include!`. Лишних файлов рядом с `.exe` не нужно. Тест
`every_fewshot_example_builds_a_valid_body` прогоняет план каждого примера на настоящей сессии,
поэтому примеры не устареют вместе с командами.

### Логи и команды

`crates/ai/src/log.rs` пишет JSON-строки (по файлу в день): запрос, все попытки с ответами и
ошибками, итоговый план, время. Папка: `FORMCRAFT_LOG_DIR/ai`, иначе
`%LOCALAPPDATA%/FormCraft/logs/ai`. Ошибка логирования запрос не ломает. Эти записи — сырьё для
будущего дообучения и разбора неудач.

`crates/ai/src/commands.rs` регистрирует в реестре сессии `ai.generate {prompt, use_selection,
apply}`, `ai.explain {feature}`, `ai.status`. Поэтому ИИ вызывается так же, как любая команда:
из UI, окна S, MCP, CLI.

### Панель Assistant

`crates/ui-egui/src/assistant.rs`. Запрос уходит в фоновый поток; поток шлёт `Progress` и итог
`Done(Proposal)` по `mpsc`, UI-поток забирает их каждый кадр (`poll`). Холст не блокируется.
Результат — запись в ленте: список фич и кнопки Принять / Отклонить. Пока запись ждёт решения,
тела превью подкрашены цветом токена `ai`. «Принять» применяет сохранённый план к настоящей
сессии (`plan::apply`) — один undo-шаг и группа; «Отклонить» просто закрывает запись.
Статус-точка в шапке берётся из `ai.status` (зелёная — сервер доступен). «Explain» на таймлайне
вызывает `ai.explain` и кладёт ответ в ленту как заметку. Если ИИ-бэкенд не создался (плохой
URL), приложение работает без ИИ и показывает сообщение «Assistant unavailable».

### UI-выравнивание (ADR 0004)

`UI_SPEC.md` стал источником правды по виду, `PLAN.md` — по раскладке и функциям. Все цвета и
размеры — токены в `crates/ui-egui/src/theme.rs` (`Tokens`, `SIZE`), без литералов в виджетах.
Светлая тема по умолчанию. Приёмка автоматизирована: `formcraft-cli screenshot all <dir>`
рендерит 8 сцен §8 без окна, тест `every_spec_scene_renders` гоняет их в CI. Результаты и
оставшиеся мелочи — в `PROGRESS.md`, «Приёмка UI-выравнивания».

### Бенчмарк

`crates/ai/src/bench.rs`, данные `crates/ai/bench/cases.json`. У каждого случая: запрос на
русском или английском, уровень (`simple` / `medium`), ожидания (габариты, объём, число
цилиндрических граней) и эталонный план. Три метрики:

- **valid** — план применился и тела корректны;
- **rebuilt** — после умножения всех параметров плана на 1,1 модель снова перестраивается без
  ошибок (план действительно параметрический, а не «замороженная» форма);
- **matched** — габариты в пределах max(0,5 мм; 2%) по каждой оси (оси сравниваются по
  возрастанию: деталь может лежать иначе), объём в пределах 3%, число цилиндрических граней
  совпадает, если задано.

Эталоны проверяются в CI (`bench_references_match_their_expectations`): если ожидание и
эталонный план расходятся, ошибся тест, а не модель. Это защита от бенчмарка, который врёт.
Модель при этом не запускается: `bench_scores_with_an_oracle_and_rejects_wrong_shapes` прогоняет
Mock-«оракул», отдающий эталоны, и проверяет, что неверная форма не засчитывается. Реальные
прогоны на Ollama идут вручную: долго и зависят от железа.

Результаты ai-bench — см. PROGRESS.md и ADR 0005.

## Как проверить

Тесты (не требуют Ollama, работают на Mock):

```
cargo test -p formcraft-ai
cargo test -p formcraft-ui-egui assistant
cargo xtask ci
```

Живой запрос. Сначала в отдельном терминале `ollama serve` и убедитесь, что модель
скачана (`ollama list`). Затем:

```
target/debug/formcraft-cli.exe ai "фланец Ø100, 4 отверстия Ø9 на Ø80, толщина 10"
```

На CPU это занимает минуты. Другая модель:

```
FORMCRAFT_AI_MODEL=qwen3:8b target/debug/formcraft-cli.exe ai "фланец Ø100, 4 отверстия Ø9 на Ø80, толщина 10"
```

(в PowerShell: `$env:FORMCRAFT_AI_MODEL = "qwen3:8b"` отдельной строкой). Бенчмарк на малой выборке:

```
cargo xtask ai-bench --limit 5 --level simple
```

Всё после `ai-bench` передаётся в `formcraft-cli ai-bench` как есть (`xtask/src/main.rs`),
поддерживаются `--limit N`, `--level simple|medium`, `--out report.json`. Не добавляйте
отдельный `--` — CLI принимает его за неизвестный аргумент. Сборка идёт в release.

Снимки интерфейса, включая панель Assistant:

```
target/debug/formcraft-cli.exe screenshot all out_dir
```

## Проверь себя

1. Почему модель возвращает план из команд, а не Python- или Rust-код?
2. Что гарантирует структурный вывод, а что нет?
3. Зачем нужен fork сессии и что происходит с документом, если нажать «Отклонить»?
4. Что делает цикл исправления и сколько попыток он делает?
5. Что такое температура и почему здесь она 0.1?
6. Зачем бенчмарк умножает параметры на 1,1?
7. Почему эталонные планы бенчмарка проверяются в CI без модели?
8. Почему генерация на этой машине медленная?

<details>
<summary>Ответы</summary>

1. План проверяется по схемам реестра до запуска, не может сделать ничего вне команд, даёт
   undo, перестроение и параметры. Ошибка — обычный `Err`, а не падение или зависание.
2. Ответ всегда разбирается как JSON нужной формы с допустимыми id команд. Осмысленность
   значений (слишком большой радиус и т. п.) не гарантируется — это ловит применение плана и
   цикл исправления.
3. Модель работает на копии, поэтому UI не блокируется и документ пользователя не меняется,
   пока он не нажал «Принять». При «Отклонить» запись в ленте закрывается, в документе нет
   никаких изменений.
4. Текст ошибки возвращается модели с просьбой дать исправленный план; максимум 3 попытки,
   потом показывается ошибка.
5. Это степень случайности выбора токенов. Низкая температура даёт стабильные и точные планы,
   важные для CAD.
6. Чтобы убедиться, что план действительно параметрический: модель с «зашитыми» числами или
   сломанными ссылками при смене размеров не перестроится.
7. Чтобы бенчмарк не врал: ожидания (габариты, объём) должны сходиться с реальным результатом
   эталонного плана. Тогда расхождение при прогоне — вина модели, а не данных.
8. Ollama не нашёл видеокарту, инференс идёт на CPU, который заметно медленнее GPU.

</details>
